# Supplier Acknowledgement Generator - Data Dictionary

## 1. Overview

This document describes the 12 CSV datasets generated by the Supplier Acknowledgement Generator.

The datasets model the procurement lifecycle, from supplier and purchase-order creation through supplier acknowledgements, delivery promises, change approvals, inventory planning, production allocations, and downstream notifications.

The project also includes four deliberately injected anomalies. These are recorded in `ground_truth.csv` so that they can be identified during validation and analysis.

## 2. Dataset Summary

| Dataset                        | Purpose                                                | Primary Key           |
| ------------------------------ | ------------------------------------------------------ | --------------------- |
| `suppliers.csv`                | Supplier master records                                | `supplier_id`         |
| `purchase_orders.csv`          | Purchase orders issued to suppliers                    | `po_id`               |
| `po_lines.csv`                 | Individual items and quantities within purchase orders | `po_line_id`          |
| `acknowledgements.csv`         | Supplier responses to purchase-order lines             | `ack_id`              |
| `promises.csv`                 | Supplier delivery-date commitments                     | `promise_id`          |
| `changes.csv`                  | Differences between requested and acknowledged terms   | `change_id`           |
| `approvals.csv`                | Approval decisions for change requests                 | `approval_id`         |
| `inventory_plan.csv`           | Versioned expected supply for each PO line             | `plan_id`             |
| `production_orders.csv`        | Production jobs requiring purchased materials          | `production_order_id` |
| `production_order_po_line.csv` | Links production orders to PO lines                    | Composite key         |
| `notifications.csv`            | Downstream supply-impact notifications                 | `notification_id`     |
| `ground_truth.csv`             | Labels for intentionally injected anomalies            | `anomaly_id`          |

## 3. Dataset Field Definitions

### 3.1 Suppliers - `suppliers.csv`

Stores the supplier master data used by purchase orders.

| Column                    | Description                         |
| ------------------------- | ----------------------------------- |
| `supplier_id`             | Unique supplier identifier          |
| `supplier_name`           | Name of the supplier                |
| `country`                 | Supplier's country                  |
| `standard_lead_time_days` | Standard delivery lead time in days |
| `reliability_score`       | Supplier reliability score          |
| `status`                  | Supplier status                     |

### 3.2 Purchase Orders - `purchase_orders.csv`

Stores purchase orders issued to suppliers.

| Column         | Description                         |
| -------------- | ----------------------------------- |
| `po_id`        | Unique purchase-order identifier    |
| `supplier_id`  | Supplier associated with the order  |
| `planner_id`   | Planner responsible for the order   |
| `order_date`   | Date the purchase order was created |
| `currency`     | Currency used for the order         |
| `status`       | Purchase-order status               |
| `total_amount` | Total purchase-order value          |

### 3.3 Purchase Order Lines - `po_lines.csv`

Stores individual items belonging to purchase orders.

| Column             | Description                           |
| ------------------ | ------------------------------------- |
| `po_line_id`       | Unique purchase-order line identifier |
| `po_id`            | Parent purchase-order identifier      |
| `line_number`      | Line number within the purchase order |
| `item_code`        | Identifier of the ordered item        |
| `item_description` | Description of the item               |
| `uom`              | Unit of measure                       |
| `ordered_qty`      | Quantity originally ordered           |
| `unit_price`       | Price per unit                        |
| `line_total`       | Total value of the line               |
| `requested_date`   | Requested delivery date               |
| `status`           | Purchase-order line status            |

### 3.4 Acknowledgements - `acknowledgements.csv`

Stores supplier responses to purchase-order lines.

| Column                 | Description                                           |
| ---------------------- | ----------------------------------------------------- |
| `ack_id`               | Unique acknowledgement identifier                     |
| `po_id`                | Purchase-order identifier                             |
| `po_line_id`           | Purchase-order line referenced by the acknowledgement |
| `revision_no`          | Acknowledgement revision number                       |
| `ack_date`             | Date the supplier acknowledged the order              |
| `accepted_qty`         | Quantity accepted by the supplier                     |
| `rejected_qty`         | Quantity rejected by the supplier                     |
| `confirmed_unit_price` | Unit price confirmed by the supplier                  |
| `ack_status`           | Acknowledgement status                                |

A purchase-order line can receive multiple acknowledgement revisions.

### 3.5 Promises - `promises.csv`

Stores delivery commitments made by suppliers.

| Column           | Description                              |
| ---------------- | ---------------------------------------- |
| `promise_id`     | Unique delivery-promise identifier       |
| `po_line_id`     | Related purchase-order line              |
| `ack_id`         | Acknowledgement that created the promise |
| `revision_no`    | Related acknowledgement revision         |
| `promised_date`  | Delivery date promised by the supplier   |
| `effective_from` | Date from which the promise is effective |

A declined line may not have a promise record.

### 3.6 Changes - `changes.csv`

Stores differences between the original purchase-order terms and the supplier's acknowledgement.

| Column                 | Description                                         |
| ---------------------- | --------------------------------------------------- |
| `change_id`            | Unique change-request identifier                    |
| `po_id`                | Related purchase order                              |
| `po_line_id`           | Related purchase-order line                         |
| `ack_id`               | Acknowledgement that caused the change              |
| `promise_id`           | Related promise identifier; optional                |
| `revision_no`          | Acknowledgement revision associated with the change |
| `change_types`         | Types of changed terms                              |
| `requested_unit_price` | Originally requested unit price                     |
| `proposed_unit_price`  | Supplier-confirmed unit price                       |
| `price_delta_pct`      | Percentage difference in unit price                 |
| `requested_qty`        | Originally ordered quantity                         |
| `proposed_qty`         | Supplier-accepted quantity                          |
| `qty_shortfall_pct`    | Percentage quantity shortfall                       |
| `requested_date`       | Originally requested delivery date                  |
| `proposed_date`        | Supplier-proposed delivery date; optional           |
| `date_slip_days`       | Difference between requested and proposed dates     |
| `breached_rules`       | Approval rules exceeded by the change               |
| `approval_required`    | Indicates whether approval is required              |
| `supersedes_change_id` | Previous change superseded by this change; optional |
| `created_date`         | Date the change request was created                 |
| `status`               | Change decision or pending status                   |

Important status meanings:

* `AUTO_APPROVED`: The change is within automatic approval thresholds.
* `APPROVED`: The change was accepted through an approval decision.
* `REJECTED`: The proposed supplier terms were not accepted.
* `PENDING_APPROVAL`: A decision has not yet been made.

A change can reference a previous change through `supersedes_change_id` when a later acknowledgement revision supersedes an earlier change for the same purchase-order line.

### 3.7 Approvals - `approvals.csv`

Stores approval decisions associated with change requests.

| Column          | Description                       |
| --------------- | --------------------------------- |
| `approval_id`   | Unique approval identifier        |
| `change_id`     | Change request being reviewed     |
| `approval_seq`  | Approval sequence number          |
| `approver_role` | Role responsible for the decision |
| `approver_id`   | Identifier of the approver        |
| `decision`      | Approval decision                 |
| `decision_date` | Date the decision was recorded    |
| `reason`        | Explanation for the decision      |

Pending changes do not have an approval record until a decision is made.

Automatically approved changes also have approval records for traceability.

In the current model, a decided change has an associated approval record. The decision is consistent with the change status.

### 3.8 Inventory Plan - `inventory_plan.csv`

Stores versioned expected supply information for each purchase-order line.

| Column             | Description                                                |
| ------------------ | ---------------------------------------------------------- |
| `plan_id`          | Unique inventory-plan record identifier                    |
| `po_line_id`       | Related purchase-order line                                |
| `item_code`        | Item being planned                                         |
| `plan_version`     | Version number for the plan                                |
| `update_type`      | Type of plan update, such as baseline or applied change    |
| `source_change_id` | Change request responsible for the update; optional        |
| `expected_qty`     | Expected supply quantity                                   |
| `expected_date`    | Expected delivery date                                     |
| `effective_from`   | Start date of the plan version                             |
| `effective_to`     | End date of the plan version; empty for the latest version |

The baseline plan represents the original ordered quantity and requested delivery date.

Subsequent plan versions are created from approved changes. Rejected and pending changes do not update the inventory plan.

Historical versions are retained rather than overwritten.

### 3.9 Production Orders - `production_orders.csv`

Stores production jobs that require materials from purchase-order lines.

| Column                | Description                                  |
| --------------------- | -------------------------------------------- |
| `production_order_id` | Unique production-order identifier           |
| `product_name`        | Product being manufactured                   |
| `planner_id`          | Planner responsible for the production order |
| `quantity_to_build`   | Planned production quantity                  |
| `need_date`           | Date materials are required                  |
| `created_date`        | Date the production order was created        |
| `status`              | Production-order status                      |

### 3.10 Production Order to PO Line - `production_order_po_line.csv`

This is the bridge dataset representing the many-to-many relationship between production orders and purchase-order lines.

| Column                | Description                                               |
| --------------------- | --------------------------------------------------------- |
| `production_order_id` | Related production order                                  |
| `po_line_id`          | Related purchase-order line                               |
| `allocated_qty`       | Quantity of the PO line allocated to the production order |

The composite key is:

`(production_order_id, po_line_id)`

The total allocated quantity for a PO line must not exceed its originally ordered quantity.

### 3.11 Notifications - `notifications.csv`

Stores notifications generated when a supply change affects a production order.

| Column                 | Description                                       |
| ---------------------- | ------------------------------------------------- |
| `notification_id`      | Unique notification identifier                    |
| `change_id`            | Change request causing the impact                 |
| `plan_id`              | Inventory-plan version associated with the impact |
| `po_line_id`           | Affected purchase-order line                      |
| `production_order_id`  | Affected production order                         |
| `recipient_planner_id` | Planner receiving the notification                |
| `impact_type`          | Type of supply impact                             |
| `days_late`            | Number of days supply is late                     |
| `shortfall_qty`        | Quantity shortfall against the allocation         |
| `severity`             | Notification severity                             |
| `created_date`         | Notification creation date                        |
| `message`              | Human-readable notification message               |
| `status`               | Notification delivery status                      |

A notification is generated when an applied change causes a delivery delay, a quantity shortfall, or both.

Notifications are directed to the planner responsible for the affected production order.

### 3.12 Ground Truth - `ground_truth.csv`

Stores the labels and references for intentionally injected anomalies.

| Column              | Description                                      |
| ------------------- | ------------------------------------------------ |
| `anomaly_id`        | Unique anomaly identifier                        |
| `anomaly_type`      | Category of injected anomaly                     |
| `entity_type`       | Type of affected entity                          |
| `record_id`         | Identifier of the affected record                |
| `related_record_id` | Identifier of a related record, where applicable |
| `description`       | Explanation of the injected anomaly              |

The four intended anomaly categories are:

1. `UNAPPROVED_CHANGE_UPDATES_INVENTORY`
2. `ACK_POINTS_TO_WRONG_PO_LINE`
3. `PROMISED_DATE_BEFORE_ORDER_DATE`
4. `OLDER_REVISION_OVERWRITES_NEWER`

These records are deliberately introduced for anomaly detection and validation testing. They should not be mistaken for ordinary generated business records.

## 4. Data Relationships

The main relationships are:

* One supplier can have many purchase orders.
* One purchase order can contain many purchase-order lines.
* One purchase-order line can receive multiple acknowledgement revisions.
* An acknowledgement can create a delivery promise.
* An acknowledgement can lead to a change request.
* A change request can have an approval decision.
* One purchase-order line can have multiple inventory-plan versions.
* Production orders and purchase-order lines have a many-to-many relationship through `production_order_po_line.csv`.
* A notification references the change, plan, purchase-order line, and production order associated with a supply impact.

### Relationship Summary

| Parent Dataset          | Related Dataset                | Relationship                                                           |
| ----------------------- | ------------------------------ | ---------------------------------------------------------------------- |
| `suppliers.csv`         | `purchase_orders.csv`          | One-to-many                                                            |
| `purchase_orders.csv`   | `po_lines.csv`                 | One-to-many                                                            |
| `po_lines.csv`          | `acknowledgements.csv`         | One-to-many                                                            |
| `acknowledgements.csv`  | `promises.csv`                 | One-to-zero-or-one in the generated model                              |
| `acknowledgements.csv`  | `changes.csv`                  | One-to-zero-or-one per acknowledgement revision in the generated model |
| `changes.csv`           | `approvals.csv`                | One-to-zero-or-one while pending; one decision record when decided     |
| `po_lines.csv`          | `inventory_plan.csv`           | One-to-many                                                            |
| `production_orders.csv` | `production_order_po_line.csv` | One-to-many                                                            |
| `po_lines.csv`          | `production_order_po_line.csv` | One-to-many                                                            |
| `changes.csv`           | `notifications.csv`            | One-to-many or none                                                    |
| `production_orders.csv` | `notifications.csv`            | One-to-many or none                                                    |

## 5. Data Conventions

* CSV files are exported using UTF-8 encoding.
* Dates are stored in ISO date format (`YYYY-MM-DD`).
* Empty values represent optional or unavailable values.
* Identifiers are used to connect related datasets.
* Inventory-plan history is maintained using version numbers and effective dates.
* Randomized generation uses a configured seed to support repeatable output.
* The four intentional anomalies are labelled in `ground_truth.csv`.
* The generated records are synthetic and do not represent real supplier transactions.

## 6. Validation Objectives

The validation process checks:

1. Expected CSV files and column structures.
2. Primary-key uniqueness.
3. Foreign-key references.
4. Acknowledgement and purchase-order-line consistency.
5. Approval and change-status consistency.
6. Change supersede-chain relationships.
7. Inventory-plan version consistency and approved-only plan updates.
8. Production allocation limits.
9. Notification relationships and recipients.
10. Numeric and date values.
11. Presence of the four required anomaly labels.

The validation process is designed to identify structural and relational data issues while also confirming that the required intentional anomalies are present and labelled.
